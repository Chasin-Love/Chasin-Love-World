## The architectural core: envelope sealing

Previously every record save re-ran the full Argon2id KDF (64 MiB × 3) —
expensive and the blocker for alternate unlock factors. The vault now uses
**envelope encryption** (`crypto.ts`, `VaultSecrets.version = 2`):

- A random 256-bit **ring key** seals the record payload (raw AES-GCM — saves
  are now instant, no KDF per keystroke).
- **Envelopes** wrap the ring key, each under its own KDF-derived key:
  - `master` — the master passphrase, optionally bound to a keyfile
    (`passphrase::sha256(file)`), with a fast fingerprint check before any KDF.
  - `prf` — a WebAuthn PRF credential (see Stargate).
  - `custodian` — the Stellar Will key.
- Legacy v1 seals (PBKDF2 or Argon2id-direct) stay fully readable and
  **migrate transparently** on the next open, with an audit entry.
- Rotation (`RotateKeyModal`) now verifies the current secret by unwrapping
  the live envelope, then re-wraps — instant, and it can bind or unbind a
  keyfile at the same time.
- Backups export as `v: 2` (still sealed, checksummed); v1 backups import
  and migrate on the spot.

## Shipped this round

### 1. Stargate — WebAuthn PRF unlock (`StargateModal`)
Enroll a platform authenticator (Windows Hello / Touch ID / security key)
from the **vault armory**. The authenticator derives a secret inside secure
hardware via the WebAuthn **PRF extension**; that secret wraps the ring key.
Afterwards the locked ring offers a **stargate button** — one glance or touch
unseals it. The master key is never stored, typed, or transmitted.
Graceful refusal with explanation when the authenticator or context
(https/localhost) lacks PRF support.

### 2. Keyfile binding (KeePass-style second factor)
Bind a keyfile during rotation; present it at unlock via a dedicated
keyfile screen (fingerprint `fp` shown so the right file can be verified
before any KDF runs). Unbind by rotating without keeping it.

### 3. The Stellar Will — dead-man's switch (`courier.ts`, `StellarWillModal`)
Arm from the armory: a random 32-byte **custodian key** is forged and shown
exactly once; the ring key is wrapped under it with a chosen darkness
threshold (3/6/12 months). Every open refreshes `lastOpenedAt`. After the
threshold passes, the locked screen offers **stellar will** — the custodian
key opens the ring (with a suggestion to rotate). Before it, the claim is
refused with the remaining days. Fully offline; a genuine grief-tech legacy
feature no mainstream rival has shipped.

### 4. The Comet Courier — one-view encrypted sharing (`courier.ts`)
- **Comet (send):** pick credentials, optionally add a note — a sealed
  `.comet.json` file downloads, and a one-time **starlight key** is shown
  once. File and key travel by different channels; the payload is useless
  without the key.
- **Receive:** open a comet + key — expiry (7-day tail) and
  **burn-after-read** (local consumed-ledger, honest about its per-machine
  scope) are enforced, duplicates are refused, and sealing lands straight
  in the ring.

### 5. Sentinel: card expiry detection
Fields like `expiry: 12/26` (or `expires`, `valid until`, MM/YYYY forms) are
parsed; expired or <90-day items surface as a **collapsing orbit** row in the
sentinel report.

### 6. Vault armory (right column)
A dedicated surface hosting stargate / will / comet / receive, with a live
status line (stargate attuned · keyfile bound · will armed · envelope-sealed).
The locked screen gains stargate + will actions.
